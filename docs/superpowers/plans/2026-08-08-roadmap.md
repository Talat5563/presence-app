# Presence — roadmap after Phase 0

**Date:** 2026-08-08
**Status:** Phase 0's harness is merged; Phase 0's *measurement* has not happened.

This sequences the work from here. It is not an implementation plan — each phase below gets its own
spec and plan when it is reached, the way Phase 0 did. What this document fixes is the **order**, the
**gates** between phases, and the **decisions that must be made before** certain phases can start.

---

## The one thing that gates almost everything

**There is no corpus.** The harness is built and tested, but it has never seen a real child's voice.
Until it does, every number in this project is a citation from a paper rather than a measurement of
*this* system on *these* children.

Two consequences worth internalising:

- **Consent scope must be settled before a single recording is made.** Whether the recordings may
  train a shipped model or only evaluate it cannot be added to a consent form retroactively. Get
  this wrong and the Hebrew data — for which no public corpus exists — can never enter the
  fine-tuning mix.
- **Everything downstream is speculative until Phase 2 returns a number.** Building UI or Android
  code first would mean betting the project on a recognizer nobody has measured.

## Phase 1 — Corpus collection

**Not an engineering task.** The protocol is spec §9.1 and it is specific: 5–10 households if
achievable (3 is the floor, since two must be held out), every sibling and both parents, ~5 minutes
of usable speech per speaker split across both languages plus code-switching plus the calling
phrases, varied distance and phone placement and background, children's television as negative
material, and a re-record after 3–6 months so age drift is measurable.

**Read `2026-08-07-phase0-execution-notes.md` before recording.** Two items will otherwise cost you a
re-collection:

- **Label every call.** An unlabelled real call in a target-child recording now scores as a false
  alarm. That is the right default — an unlabelled corpus must not flatter the result — but it
  biases the verdict pessimistically, and the harness will warn you rather than silently absorb it.
- **Synthetic audio is useless here.** Silero rates a pure tone *below* silence; a synthetic smoke
  corpus produces zero detections and looks exactly like a broken pipeline.

**Exit criterion:** `recordings.csv` and `events.csv` load without error, at least three households,
at least two held out.

## Phase 2 — First measurement

Run the harness on the dev set, read `report.md`. This is cheap and it is the decision point the
whole project has been arranged around.

```bash
./gradlew :harness:run --args="--manifest data --models models --out reports/dev --holdout h3,h4"
```

**What the verdict means:**

- **SHIP** — proceed to Phase 4, then 5/6. Do not skip fine-tuning entirely; it is cheap insurance
  and the shipped model gets better for free.
- **ITERATE** — proceed to Phase 3. Expected outcome, given the literature.
- **FALL_BACK** — **go to Phase 3, not to tuning.** Fine-tuning is worth roughly an order of
  magnitude; no amount of threshold fiddling substitutes for it. Only if Phase 3 also falls back
  does the product need rethinking, and Phase 7 is the answer there.

**Both languages must clear the bar independently.** A system that passes in English and fails in
Hebrew has one working language and one that will erode a parent's trust in the whole app.

**Do not read the holdout number yet.** Choose the operating point here, measure it once on the
holdout at the end. The CLI enforces this — `--evaluate holdout` requires an explicit `--threshold`.

## Phase 3 — L3 model fine-tuning

The single largest lever available: an adult-trained model measures ~31% EER on children's
spontaneous speech; the same architecture fine-tuned on children's speech reaches 2.9%.

**Entirely offline, in Python.** It produces a better `.onnx` file with the same tensor shapes —
nothing in the Kotlin changes, and you re-run the same harness to compare. WeSpeaker was chosen for
exactly this reason: it trains in PyTorch and exports ONNX as a drop-in replacement.

**Training mix**, split by what actually transfers across languages:

| Source | Provides |
|---|---|
| Samrómur Children (CC BY 4.0, 131 h, 3,175 speakers aged 4–17) | Child vocal-tract characteristics — generalises from Icelandic |
| ivrit.ai Hebrew adult speech, warped with ChildAugment | Hebrew phonetics with child-like vocal tracts — this does *not* transfer |
| Your recordings, if consent allows | Real bilingual children in real rooms |

**Its plan will cover:** the Python training pipeline, the ChildAugment implementation and its
parameter ranges, the ONNX export and shape verification, a held-out comparison against the current
model on the same corpus, and licence verification for everything that ships.

**Attribution is a licence condition** if Samrómur is used — it must appear in the app's about
screen, not only in the repository.

## Phase 4 — Calibration sweep

The harness sweeps `fireThreshold` today. The infrastructure for sweeping the matcher's own knobs
exists — `MatchScore` is cached per observation and gating is centralised in `applyGates` — but the
sweep itself is not wired up.

**Why it matters:** `minTargetSimilarity` (default 0.35) is the most important open-set knob and is
completely unvalidated. The only signal so far is that synthetic separation ran *hot* — 0.99
same-speaker against 0.83 for entirely different signals — which suggests the real separation band
may be narrower and higher than assumed. A wrong value here means either a stranger triggers the app
or your own child never does.

Small phase, high leverage. Fold it into Phase 3's plan if that is more convenient.

## Phase 5 — UI design (delivered)

In `docs/design/`: tokens, 298 bilingual strings, 31 screen specs, a component inventory, and
mockups. Delivered as tokens and specs rather than pictures, which is what Compose can consume.

**Two things remain before Phase 6 can use it:**

- **The Hebrew is a placeholder**, written to size the layout rather than to ship. The handoff says
  so itself. Every string carrying an `intent` note needs a native Hebrew speaker who reads the
  intent and reaches for the feeling — tone does not survive translation, and tone is this app's most
  fragile quality. This is the one part of the project a model should not have the last word on.
- **`INTEGRATION_GAPS.md`** records where the design and the engine disagree, including two decisions
  that block planning this phase.

## Phase 6 — Android app

The largest build, and the one most exposed to platform reality rather than algorithms.

**Start from `docs/design/INTEGRATION_GAPS.md`.** The design handoff was checked against the spec and
the engine as built. Both blocking decisions are now resolved — single target child, ducking on both
platforms — and the three engine gaps that changed types the whole app binds to (E1 "not them" data
path, E2 additive re-enrollment, E3 cooldown and dismissal) were fixed on 2026-10-28. E4–E6 remain,
and are small or naturally part of this phase's persistence and enrollment work.

**Its plan will cover:** the foreground service with microphone type, screen-state gating, the
overlay intervention (dim scrim and photo in one window), audio ducking and DND, staged permission
onboarding across four separate trips into system Settings, the enrollment and household-setup
flows, settings and the response builder, SQLDelight storage, and the `androidMain` actuals for
audio capture and ONNX Runtime.

**Where it will actually hurt**, none of which reproduces in an emulator:

- OEM battery managers killing the foreground service — the single biggest real-world failure mode.
- The four Settings round-trips, each of which lands on a differently-named screen per manufacturer.
- The overlay behaving differently across OEM skins.

Plan on a real device early. This is also the point at which the Android tooling becomes worth
loading.

## Phase 7 — Wake-phrase channel (L5)

Query-by-Example keyword spotting: the parent records the child saying *"אבא"* or *"Mummy"* a few
times, and detection is acoustic similarity to those recordings. **No language-specific model**, so
Hebrew costs nothing extra.

It has two possible roles, and Phase 2 decides which:

- **As a feature**, it is the high-precision fast path for the most common event — a child calling
  their parent by name — alongside the text-independent channel.
- **As the fallback product**, if text-independent accuracy proves inadequate even after
  fine-tuning. A wake-phrase detector with a speaker check is narrower, but it is a genuinely useful
  product and a far more honest one than a detector that cries wolf.

The enrollment recordings serve both purposes at once, which is why the enrollment flow already asks
the child to "call me the way you normally do".

---

## Phase 8 — iOS

**Tier 1 ships without asking Apple anything:** `AVAudioSession` ducking, a Live Activity putting the
child's face in the Dynamic Island, and a Time-Sensitive notification that pierces Focus modes.
Ducking replaces muting; the Dynamic Island replaces the overlay. A close translation, not a stub.

**Tier 2 needs the Family Controls entitlement**, which Apple grants selectively. It unlocks two
things at once: a real `Block` intervention, and — more importantly — `DeviceActivityMonitor`, iOS's
only viable signal for "the parent is using their phone right now". Without it, iOS cannot detect
screen-on state at all, and the family-time schedule becomes the *only* bound on listening.

**Design for Tier 1 standing alone.** The entitlement is not a certainty, and a product that only
works if Apple says yes is not a plan.

## What could kill this, and when you would find out

**Phase 2, after fine-tuning in Phase 3.** If the system still falls back — too many false alarms, or
too few real calls caught — then text-independent recognition of a specific child in a real home is
not viable with current models, and the product becomes Phase 7: a wake-phrase detector.

That is the honest failure mode, and the whole point of building the harness before the app was to
reach it in weeks rather than after a year of UI work. The cost of finding out is now a corpus and
an afternoon.
